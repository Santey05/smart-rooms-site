## 0. Важное изменение архитектуры (2026-09-26)

Проект переведён с собственного движка бронирования и оплаты на **встроенный
модуль бронирования Bnovo** (`reservationsteps.ru` / `widget.reservationsteps.ru`).

Причина: вся информация о номерах, ценах и занятости в любом случае живёт в
Bnovo (Channel Manager), потому что через него идут брони с Booking,
Островка и других OTA. Модуль бронирования Bnovo уже включён в тариф отеля
(Старт/Рост/Максимум) и решает синхронизацию, оплату, отмену и возврат сам,
без покупки API2 «Профессионал» (34 000 ₽/год) и без самописной защиты от
двойного бронирования.

Это радикально уменьшает объём и риск проекта: своя логика бронирования,
платежей, hold'ов, возвратов и вебхуков **не разрабатывается**. Сайт
становится контентной витриной с врезанным модулем Bnovo:

```text
                    ┌───────────────────┐
                    │       Bnovo       │
                    │                   │
                    │ Типы номеров      │
                    │ Цены              │
                    │ Доступность       │
                    │ Брони             │
                    │ Оплата            │
                    │ Отмена / возврат  │
                    └─────────┬─────────┘
                              │
                           iframe
                              │
                              ▼
┌───────────────────────────────────────────────────┐
│                  Сайт отеля (Next.js)              │
│                                                     │
│  Главная · Номера (контент) · Контакты · SEO       │
│                                                     │
│        ┌───────────────────────────────┐           │
│        │   Модуль бронирования Bnovo   │           │
│        │   (страница /booking)         │           │
│        └───────────────────────────────┘           │
└───────────────────────────────────────────────────┘
```

Старая архитектура (Prisma/SQLite, ЮKassa, свои статусы бронирования и т.д.)
полностью описана в разделе **90. Архив: архитектура собственного движка
бронирования**. Раздел 90 сохранён на случай, если в будущем бизнес решит
отказаться от модуля Bnovo и делать бронирование самостоятельно (например,
при кратном росте числа номеров).

> ⚠️ **РАЗДЕЛ 90 — АРХИВ, НЕ РЕАЛИЗОВЫВАТЬ.**
> Это не текущее ТЗ. При разработке текущей версии сайта не использовать
> оттуда `Prisma`, `BookingService`, `PaymentProvider`, модели `Booking` /
> `Payment` / `Refund` и любые другие требования раздела 90. См. предупреждение
> в начале раздела 90.

Проверено вживую (тестовое бронирование в боевом Bnovo отеля, бронь

рабочий, параметры инициализации, поля гостя и вставка через `iframe`
подтверждены.

## 1. Назначение проекта

Сайт небольшого отеля с:

* публичной частью сайта (главная, контакты, правила проживания);
* общим блоком «Номера» на главной, ведущим в бронирование (см. раздел 5 —
  отдельного каталога номеров с собственными фото/описаниями на сайте нет);
* онлайн-бронированием и онлайн-оплатой **через встроенный модуль
  бронирования Bnovo**;
* SEO-оптимизированной главной страницей.

Отель небольшой:

* 7 физических номеров, сгруппированных в несколько **типов размещения**
  (в терминах Bnovo — room type; см. раздел 5);
* ожидаемая нагрузка — ориентировочно до 2–3 бронирований в сутки;
* основная валюта — RUB;
* основной язык интерфейса — русский;
* часовой пояс отеля — Europe/Moscow;
* все брони, тарифы, цены, доступность номеров, оплата, отмены и возвраты
  ведутся **в Bnovo**, не на сайте.

Проект должен быть простым в эксплуатации. Никакой собственной базы данных
броней/платежей/гостей на первом этапе не требуется — это одно из главных
архитектурных решений проекта.

## 2. Основные технологические решения

Использовать:

* Next.js;
* React;
* TypeScript;
* Tailwind CSS;
* shadcn/ui;
* Playwright для E2E-тестов;
* Sentry для мониторинга ошибок фронтенда.

Использовать `pnpm`.

Модуль бронирования Bnovo подключается как встроенный `<iframe>` через
официальный скрипт:

```html
<script src="https://widget.reservationsteps.ru/iframe/library/dist/booking_iframe.js"></script>
```

и инициализацию `BookingIframe({...}).init()` (см. раздел 6).

### 2.1. Что НЕ используется на этом этапе

Не добавлять без отдельного решения бизнеса:

* Prisma / ORM;
* SQLite / PostgreSQL / любую БД для броней, гостей, платежей;
* ЮKassa или другой платёжный провайдер напрямую на сайте (оплата — через
  платёжный шлюз, подключённый внутри Bnovo);
* Resend / собственные email-уведомления о бронировании (письма гостю
  отправляет Bnovo);
* собственную модель `Booking`, `Payment`, `Refund`, `WebhookEvent`;
* собственную проверку доступности номеров или расчёт цены.

Эти пункты подробно описаны в архиве (раздел 90) и могут понадобиться, если
проект в будущем откажется от модуля Bnovo.

### 2.2. Что может понадобиться для контента

Решено (2026-09-26): вся информация о номерах (названия типов, описания,
фото, удобства, цены) ведётся администратором **в личном кабинете Bnovo**,
а не на сайте. Сайт не хранит и не дублирует эти данные — см. раздел 5.

Остаётся только контент общего сайта, не привязанный к конкретным номерам:
главная (маркетинговый текст, фото отеля/территории), «О отеле», контакты,
правила проживания, политика конфиденциальности.

* headless CMS **или** MDX/JSON-файлы в репозитории — для этого общего
  контента, если администратор должен редактировать его сам без разработчика;
* оптимизация изображений сайта (`next/image` или аналог) — фото для
  дизайна главной/страниц, не фото конкретных номеров (те приходят из
  Bnovo, см. раздел 5).

Решение о CMS для общего контента сайта принимается отдельно, до этапа 2
(раздел 17), и не блокирует раздел про номера.

## 3. Общий принцип архитектуры

Сайт — простое Next.js-приложение без бизнес-логики бронирования:

```text
UI (страницы, компоненты)
 ↓
Контент номеров (MDX/JSON или CMS)
 ↓
Встроенный модуль бронирования Bnovo (iframe)
```

Разделять на модули имеет смысл только по контенту (страницы номеров,
главная, статьи), а не по доменной логике бронирования — её на сайте нет.

### 3.1. Mobile-ready

Мобильное приложение по-прежнему не реализуется в MVP. Поскольку вся
бизнес-логика бронирования живёт в Bnovo, а не в собственном Public API,
пункт про единый Public API/Actor-абстракцию (актуальный только для
собственного движка, раздел 90.3) в MVP не реализуется. Если в будущем
понадобится собственный API (см. раздел 90), эти принципы стоит поднять
заново.

## 4. Бронирование

Бронирование **полностью выполняется модулем Bnovo**, встроенным на
страницу сайта. Администратор ничего не делает вручную сверх того, что и
так делает в Bnovo для броней с других каналов.

### 4.1. Жёсткое архитектурное правило

**Собственная форма сайта ничего не проверяет и ничего не рассчитывает.**
Она только собирает исходные параметры поиска и передаёт их модулю Bnovo:

```text
дата заезда
дата выезда
количество взрослых
количество детей
тип номера (опционально)
промокод (опционально)
```

Сайт не выполняет проверку доступности, не считает стоимость, не хранит
результат — вся эта логика принадлежит модулю Bnovo. Если в ходе разработки
возникает соблазн добавить собственную валидацию доступности или расчёт
цены «в дополнение» к модулю — это нарушение архитектуры проекта (см. также
раздел 16).

### 4.2. Процесс с точки зрения гостя

```text
Гость на сайте выбирает даты, число гостей (своя форма или мини-виджет)
 ↓
Переход на страницу /booking с параметрами (даты, гости, тип номера)
 ↓
Встроенный модуль Bnovo показывает актуальные номера и цены
 ↓
Гость выбирает номер и тариф внутри модуля
 ↓
Гость вводит данные (имя, фамилия, телефон, email) внутри модуля
 ↓
[если включена онлайн-оплата] Оплата через платёжный шлюз, подключённый в Bnovo
 ↓
Подтверждение брони — показывается внутри модуля,
письмо гостю отправляет Bnovo
 ↓
Бронь и занятость номера сразу видны в Bnovo,
дата закрывается на всех подключённых каналах (OTA)
```

Источник истины для доступности номеров, цен, статуса оплаты и подтверждения
брони — **Bnovo**, а не сайт.

### 4.3. Что сайт передаёт в модуль

См. раздел 6.1 для полного списка параметров и примера кода.

### 4.4. Чего сайт не делает

* не проверяет доступность номеров сам;
* не рассчитывает стоимость;
* не хранит бронь, статус оплаты, данные гостя;
* не отправляет письма о бронировании;
* не обрабатывает отмену/возврат — это происходит внутри модуля/личного
  кабинета Bnovo, куда гость попадает по ссылке «Гости.биново» после брони.

## 5. Номера — решено НЕ дублировать контент Bnovo на сайте (2026-09-26)

**Вся информация о номерах — названия типов, описания, фото, удобства,
цены и наличие — ведётся администратором в личном кабинете Bnovo.** Сайт
не хранит, не редактирует и не отображает эту информацию отдельно от
модуля. Причина: два места редактирования одного и того же контента
(сайт + Bnovo) неизбежно расходятся — администратор правит только Bnovo,
а сайт всегда должен показывать актуальные данные оттуда.

Практическое следствие: **на сайте нет отдельных страниц/карточек номеров
с собственными фото и описаниями и нет модели `RoomContent`.** Каталог
номеров как таковой на сайте не строится — см. раздел 7.

### 5.1. Как это выглядит для гостя

Вместо каталога карточек номеров — один общий блок «Номера» на главной
странице:

* маркетинговый текст и фото самого отеля/территории/общих зон (это
  контент дизайна сайта, раздел 2.2, не привязан к конкретным типам
  номеров);
* одна кнопка **«Смотреть номера и цены»** (или «Забронировать»), ведущая
  на `/booking` без фильтра по типу номера.

На `/booking` встроенный модуль Bnovo сам показывает все типы номеров с их
актуальными фото, описаниями, ценами и наличием — так же, как это было
подтверждено на тестовом бронировании (раздел 0). Дублировать этот список
на сайте не нужно.

### 5.2. Терминология: тип номера vs физический номер

Если в будущем понадобится ссылка на конкретный тип номера (например, из
письма или рекламной кампании), важно не путать понятия:

* в Bnovo единица бронирования — **тип номера (room type)**, а не
  физическая комната; у отеля 7 физических номеров, сгруппированных в
  несколько типов размещения;
* `bnovoRoomTypeId` — ID **типа номера** в Bnovo;
* параметр `rooms` в модуле (раздел 6.1) — идентификатор типа номера для
  фильтрации результатов, а не номера конкретной комнаты.

Хранить где-либо на сайте *описания* типов номеров не требуется (раздел
5.1), но если понадобится точечная ссылка «сразу в этот тип номера»,
`bnovoRoomTypeId` можно передать в параметр `room` формы (раздел 6.2) без
создания отдельной контентной модели — просто как строковую константу или
переменную окружения на конкретной маркетинговой странице/баннере.

### 5.3. Цены нигде на сайте не показываются

Поскольку сайт не хранит данные о номерах, цену показывать негде и не из
чего — ни точную, ни ориентировочную «от N ₽». Актуальную цену гость видит
только внутри модуля на `/booking`, где она приходит напрямую из Bnovo.

## 6. Встраивание модуля бронирования

### 6.1. Страница `/booking`

```tsx
"use client";
import Script from "next/script";
import { useSearchParams } from "next/navigation";

const BNOVO_UID = process.env.NEXT_PUBLIC_BNOVO_UID!; // "f88eee98-...-...-...-..."

export function BnovoBooking() {
  const params = useSearchParams();

  return (
    <>
      <div id="bnovo_booking" />
      <Script
        src="https://widget.reservationsteps.ru/iframe/library/dist/booking_iframe.js"
        strategy="afterInteractive"
        onReady={() => {
          // @ts-expect-error — глобальный класс из внешнего скрипта Bnovo
          new window.BookingIframe({
            html_id: "bnovo_booking",
            uid: BNOVO_UID,
            lang: "ru",
            width: "auto",
            height: "auto",
            rooms: params.get("room") ?? "",       // ID типа номера Bnovo — см. 5.1
            dfrom: params.get("dfrom") ?? "",
            dto: params.get("dto") ?? "",
            adults: params.get("adults") ?? "2",
            children: params.get("children") ?? "", // см. 6.4 — не путать с adults
            promoCode: params.get("promoCode") ?? "",
          }).init();
        }}
      />
    </>
  );
}
```

Полный список параметров инициализации модуля (подтверждено на практике):

| Параметр | Назначение |
|---|---|
| `html_id` | id DOM-элемента-контейнера |
| `uid` | идентификатор объекта размещения в Bnovo (обязателен) |
| `lang` | язык интерфейса (`ru`, `en`, ...) |
| `width`, `height` | `auto`, `Npx` или `N%` |
| `rooms` | ID **типа номера** Bnovo — фильтр результатов (см. 5.1) |
| `dfrom`, `dto` | даты заезда/выезда в формате `DD-MM-YYYY` |
| `adults`, `children` | число гостей — см. 6.4 |
| `promoCode` | промокод, если используется — см. 6.5 |

`BNOVO_UID` хранится в переменной окружения (публичный идентификатор
объекта размещения в Bnovo, не секрет, но конфигурируемый — на случай смены
объекта или тестового/боевого окружения).

### 6.2. Своя форма поиска (главная, страница номера)

Обычная форма-навигация, без бизнес-логики (см. правило раздела 4.1):

```tsx
function goToBooking(values: {
  dfrom: string;       // DD-MM-YYYY
  dto: string;
  adults: number;
  children?: number;
  room?: string;        // bnovoRoomTypeId, см. 5.1
  promoCode?: string;
}) {
  const q = new URLSearchParams({
    dfrom: values.dfrom,
    dto: values.dto,
    adults: String(values.adults),
    ...(values.children ? { children: String(values.children) } : {}),
    ...(values.room ? { room: values.room } : {}),
    ...(values.promoCode ? { promoCode: values.promoCode } : {}),
  });
  router.push(`/booking?${q.toString()}`);
}
```

### 6.3. Технические детали, подтверждённые проверкой

* Скрипт `booking_iframe.js` использует `iFrameResizer` — высота `iframe`
  подстраивается под контент автоматически, отдельно решать проблему
  скролла внутри iframe не требуется.
* На мобильных модуль может редиректить на отдельную полноэкранную страницу
  вместо iframe (поведение зависит от настроек Bnovo/скрипта) — проверить
  на реальном устройстве перед запуском и при необходимости настроить в
  личном кабинете Bnovo.
* Модуль сам собирает `utm_source/utm_medium/utm_campaign/utm_term/utm_content`
  из URL страницы, где встроен — дополнительная аналитика на сайте не
  обязательна для атрибуции источника брони.
* Валидация параметров происходит на стороне скрипта Bnovo (например,
  `uid` обязан быть валидным UUID) — сайт должен передавать корректные
  значения, но не обязан дублировать эту валидацию.

### 6.4. `adults` и `children` — не преобразовывать самостоятельно

Bnovo различает количество взрослых (`adults`) и детей (`children`) как
отдельные параметры, а не общее число гостей. **В MVP форма поиска на сайте
использует эти два поля в соответствии с моделью Bnovo.** Не суммировать их
в одно «количество гостей» и не пытаться на стороне сайта проверять,
вмещает ли номер такое количество человек — это делает модуль Bnovo при
показе доступных номеров (особенно важно для трёхместного и шестиместного
номеров отеля).

### 6.5. Промокоды — решить явно перед реализацией

Параметр `promoCode` поддерживается модулем технически (см. таблицу в 6.1),
но использование промокодов в MVP — отдельное решение бизнеса, ещё не
принятое. Пока оно не принято:

* поле ввода промокода на сайте (вне модуля) **не реализовывать**;
* параметр `promoCode` в коде инициализации (6.1) оставлен для полноты, но
  передаётся пустым, если не заполнен через query-параметр;
* не создавать наполовину реализованный механизм — либо промокоды заводятся
  полностью (форма ввода на сайте, поле в query-параметрах `/booking`,
  проверка результата в Bnovo вручную администратором), либо не
  используются вовсе на этом этапе.

### 6.6. Известные нюансы (проверено вживую)

* **Маска телефона в форме модуля может подставлять код другой страны**,
  если номер введён без `+7` в начале. Указывать в подсказке над полем
  телефона на сайте (в собственном UI перед переходом в модуль, если такое
  поле есть) формат `+7 9XX XXX-XX-XX`, либо предупредить пользователя внутри
  инструкции для администратора, чтобы он перепроверял телефон в новых

## 11. Безопасность и персональные данные

### 11.1. Общие требования

* HTTPS;
* секреты (если появятся — например, ключ CMS) не хранить в Git;
* не размещать на странице `/booking` сторонние скрипты, не связанные с

  iframe модуля.

### 11.2. Content-Security-Policy

CSP должен разрешать ресурсы, необходимые модулю Bnovo: `script-src`,
`frame-src`, при необходимости `connect-src`, `img-src`, `style-src` и
другие директивы. **Точный набор доменов определить по фактическим сетевым
запросам `booking_iframe.js` и iframe в тестовом/production окружении** —
не фиксировать заранее только `widget.reservationsteps.ru` и
`reservationsteps.ru`: модуль внутри может обращаться к дополнительным
доменам (шрифты, аналитика, платёжный шлюз). Не разрешать `*` без
необходимости.

### 11.3. Персональные данные (152-ФЗ)

Данные гостя и платёжные данные вводятся непосредственно в модуле Bnovo —
сайт не должен самостоятельно дублировать сбор этих данных без
необходимости (например, не делать параллельную форму «оставить заявку» с
теми же полями вне модуля без явной причины).

Это **не означает**, что у сайта нет собственных обязательств по обработке
персональных данных: сайт может обрабатывать IP-адреса, cookies,
аналитические идентификаторы, UTM-метки, технические логи, а в будущем —
данные из собственных форм, если они появятся. Распределение обязанностей
по обработке персональных данных между сайтом, владельцем отеля и Bnovo
необходимо определить отдельно, в соответствии с фактической схемой
обработки данных (какие cookie/аналитика используются на сайте, какая
политика конфиденциальности публикуется, кто выступает оператором для
каких категорий данных) — это не решается автоматически фактом встраивания
iframe.

## 12. Тестирование

### 12.1. Автоматически (Playwright E2E)

```text
Открыть главную → выбрать даты в форме поиска → перейти на /booking
  → убедиться, что параметры (даты, adults, children) корректно переданы в модуль
  → убедиться, что iframe модуля загрузился и виден
```

Полный сценарий оплаты и подтверждения брони **не тестируется E2E на
сайте** — это находится внутри модуля Bnovo (сторонний iframe), вне
контроля тестов проекта. Не создавать хрупкие тесты, кликающие внутрь
чужого iframe.

### 12.2. Unit-тесты

* формирование query-параметров для `/booking` из формы поиска (включая
  раздельные `adults`/`children`, см. 6.4);
* рендер общего контента сайта (главная, контакты и т.д.) из MDX/JSON/CMS,
  если он используется.

### 12.3. Обязательный ручной acceptance-тест перед production

**Успешная загрузка iframe модуля НЕ является подтверждением
работоспособности бронирования.** Интеграция считается подтверждённой
только после прохождения полного ручного сценария на реальном (тестовом
или боевом, с последующей отменой) аккаунте Bnovo:

```text
1. Выбрать реальные даты на сайте → перейти в /booking
2. Выбрать номер и тариф внутри модуля
3. Проверить, что показанная цена соответствует ожиданиям
4. Ввести данные гостя
5. Пройти оплату (если предоплата включена)
6. Получить подтверждение брони внутри модуля
7. Проверить письмо гостю
8. Проверить, что бронь появилась в личном кабинете Bnovo
9. Проверить, что номер/даты закрылись в доступности (шахматка Bnovo)
10. Проверить отмену брони и (если применимо) возврат
```

Этот сценарий обязателен перед каждым запуском в production и после любых
изменений в параметрах интеграции (раздел 6.1) или в личном кабинете Bnovo,
влияющих на модуль (тарифы, шлюз оплаты и т.д.).

## 18. Главный принцип проекта

При любом изменении сначала учитывать: корректность передачи параметров в
модуль бронирования Bnovo; отсутствие собственной логики доступности/цены,
дублирующей Bnovo; простоту поддержки контентного сайта; SEO и скорость
загрузки страниц.

работоспособности бронирования.** Работоспособность интеграции считается

получение уведомления → закрытие доступности → проверка отмены.

Не восстанавливать собственную бизнес-логику бронирования (раздел 90) без
явного решения бизнеса — это осознанный отказ от лишней сложности и рисков
двойного бронирования, а не временное упрощение.

Если требования неоднозначны, не придумывать бизнес-правила самостоятельно.
Сначала уточнить, как это работает в личном кабинете Bnovo, и только потом
реализовывать интеграцию на сайте.

## 90. Архив: архитектура собственного движка бронирования

> Этот раздел не является текущим ТЗ. Не использовать требования этого

> решения об этом ничего из раздела 90 не реализуется, включая частичное
> использование отдельных сущностей (`Booking`, `Payment`, `RatePlan` и т.д.).

Ниже — полная архитектура, разработанная до перехода на модуль
бронирования Bnovo (раздел 0). Она **не реализуется** на текущем этапе и
хранится как готовый план на случай, если в будущем бизнес откажется от
модуля Bnovo (например, при существенном росте числа номеров или при

Если проект вернётся к этой архитектуре, потребуется отдельно решить, как
она будет синхронизироваться с Bnovo как channel manager (собственный API
v2 «Профессионал», iCal-экспорт/импорт занятости, или полный отказ от
Bnovo).

### 90.1. Технологии собственного движка

* Prisma ORM;
* SQLite на первом этапе, с возможностью перехода на PostgreSQL;
* ЮKassa для онлайн-оплаты (банковская карта, СБП);
* Resend для email-уведомлений.

### 90.2. Принцип архитектуры

```text
Transport layer
(Next.js Server Components, Public API)
 ↓
Application Service
 ↓
Domain / Business Rules
 ↓
Repository
 ↓
Prisma
 ↓
SQLite
```

Интеграции (`PaymentProvider`, `EmailProvider`) — через абстракции.

### 90.3. Mobile-ready architecture

Единый Public API для Web и Mobile; SSR через прямой вызов Application
Services; клиентские операции через Public API; единая бизнес-логика без
дублирования правил между клиентами; `Actor`-абстракция авторизации:

```ts
type Actor =
  | { type: "GUEST"; bookingId: string }
  | { type: "ADMIN"; adminId: string };
```

`Actor` строится только транспортным слоем после аутентификации; `bookingId`
от клиента сам по себе не является авторизацией (защита от IDOR).

### 90.4. Бронирование — процесс

```text
Выбор дат → Выбор номера → Выбор тарифа → Ввод данных гостя
 → Серверная проверка → Расчёт стоимости на сервере
 → Временная блокировка → Создание платежа → ЮKassa → Оплата
 → Webhook ЮKassa → Проверка платежа → CONFIRMED → Уведомления
```

Возврат с платёжной страницы — не подтверждение оплаты. Источник истины —
серверная обработка webhook.

### 90.5. Статусы бронирования

`PENDING_PAYMENT`, `CONFIRMED`, `CANCELLED`, `COMPLETED`, `EXPIRED`.

`COMPLETED` в MVP выставляется только вручную администратором, без
автоматического воркера.

### 90.6. Временная блокировка номера

```env
PAYMENT_HOLD_MINUTES
```

`PENDING_PAYMENT → EXPIRED` обрабатывается лениво, без отдельного
воркера/cron.

### 90.7. Защита от двойного бронирования

Сервер обязан повторно проверять даты, доступность, действующие брони,
активные hold'ы, тариф, стоимость. Транзакции и constraint'ы БД,
совместимые с SQLite и PostgreSQL.

**Полуоткрытый интервал** `[checkIn, checkOut)`:

```text
existing.checkIn < requested.checkOut
AND
existing.checkOut > requested.checkIn
```

Блокируют номер: `PENDING_PAYMENT` (если `expiresAt > now`), `CONFIRMED`.
Не блокируют: `CANCELLED`, `COMPLETED`, `EXPIRED`.

### 90.8. Номера

```text
Room
- id
- number
- name
- description
- capacity
- active
- createdAt
- updatedAt
```

Цена не хранится в `Room` — см. 90.10.

### 90.9. Тарифы

```text
RatePlan
- id
- name
- description
- refundable
- freeCancellationHours
- refundPolicy   (FULL_BEFORE_DEADLINE | NON_REFUNDABLE)
- active
```

```text
RoomRatePlanPrice
- id
- roomId
- ratePlanId
- pricePerNight   (копейки)
- active
```

#### Snapshot условий тарифа в бронировании

```text
Booking
- ratePlanId
- ratePlanNameSnapshot
- pricePerNightSnapshot
- cancellationDeadline
- refundPolicySnapshot
```

`cancellationDeadline` вычисляется один раз при создании `Booking`:

```text
checkInDate + HotelSettings.checkInTime − freeCancellationHours
(в таймзоне Europe/Moscow)
```

и не пересчитывается после создания брони.

### 90.10. Ценообразование

```text
Room + RatePlan → RoomRatePlanPrice.pricePerNight × nights
  − Discount (не более одной) → Final price
```

Цена рассчитывается только сервером.

Финансовый snapshot бронирования:

```text
Booking
- pricePerNightSnapshot
- nights
- subtotalSnapshot
- discountTypeSnapshot?
- discountCodeSnapshot?
- discountAmountSnapshot
- finalAmount
```

После создания брони историческая сумма никогда не пересчитывается по
текущим `Promotion`/`PromoCode`/`RoomRatePlanPrice`.

### 90.11. Акции и промокоды

```text
Promotion
- id, name, description, discountType (PERCENT|FIXED_AMOUNT), value
- startsAt, endsAt, active
```

```text
PromoCode
- id, code, discountType, value
- startsAt, endsAt, usageLimit, usageCount, active
```

Проверяются и применяются на сервере. Не более одной скидки на бронь —
выбирается большая. `usageCount` инкрементируется атомарно
(`UPDATE ... WHERE usageCount < usageLimit`).

### 90.12. Платежи

```ts
interface PaymentProvider {
  createPayment(...): Promise<...>
  getPayment(...): Promise<...>
  refundPayment(...): Promise<...>
}
```

Идемпотентность `createPayment` — через application-level idempotency key
и/или idempotency key ЮKassa.

### 90.13. Модель платежа

Статусы: `PENDING`, `PAID`, `FAILED`, `EXPIRED`, `REFUND_PENDING`,
`REFUNDED`. Несколько попыток оплаты на одну бронь; только один платёж
может быть успешным.

### 90.14. Webhook ЮKassa

Проверка подлинности, идемпотентность через отдельную сущность:

```text
WebhookEvent
- id, provider, providerEventId, eventType, processedAt, createdAt
```

Уникальный индекс `(provider, providerEventId)`.

### 90.15. Отмена и возврат

Единый метод для гостя и администратора:

```ts
BookingService.cancelBooking({ bookingId, actor, reason?, refundOverride? })
```

Правила возврата:
* возвратный тариф до дедлайна → 100% возврат;
* возвратный тариф после дедлайна → 0%;
* невозвратный тариф → отмена разрешена, возврат не создаётся;
* `PENDING_PAYMENT` → отмена без возврата, hold снимается.

`Refund`:

```text
Refund
- id, bookingId, paymentId, providerRefundId?
- amount, status (PENDING|SUCCEEDED|FAILED)
- idempotencyKey, reason?, createdAt, updatedAt
```

Admin override возврата — только `actor=ADMIN`, обязательный `reason`,
обязательное логирование, проверка границ суммы:

```text
0 <= refundOverride.amount <= Payment.amount
сумма всех успешных/ожидающих возвратов + новый <= Payment.amount
```

**Инвариант:** `CANCELLED` необратим — поздний webhook `PAID` после отмены
не переводит бронь обратно в `CONFIRMED`; вместо этого создаётся
автоматический возврат.

### 90.16. Повторная оплата

`FAILED` платёж не создаёт новую бронь — только новую попытку оплаты для
существующей.

### 90.17. Доступ гостя без регистрации

```text
/booking/<secure-token>
```

Токен — хеш в БД, PII не в URL, ограниченный срок действия, защита от
перебора, возможность отзыва.

### 90.18. Данные гостя

Минимально необходимые PII: имя, email, телефон, данные бронирования. Не
собирать лишнее, не помещать PII в URL/логи/telemetry без необходимости.

### 90.19. Административная панель

Роль `ADMIN`: брони, номера, тарифы, цены, акции, промокоды, платежи,
возвраты, отмена (через `BookingService.cancelBooking()`).

### 90.20. Авторизация администратора

Email + пароль, защищённая сессия, хеш пароля, защита от brute-force,
rate limiting, logout, проверка роли на сервере.

### 90.21. Индексы БД

Брони (номер, даты, статусы), платежи, возвраты, payment provider ID,
webhook event ID, промокоды, email, secure token hash.

### 90.22. Тестирование

**Unit:** расчёт стоимости, ночей, промокода/акции, формула пересечения
дат, `cancellationDeadline` vs `expiresAt`, границы `refundOverride`.

**Integration:** создание брони, hold, повторная оплата, webhook
(идемпотентность), отмена, возврат, конфликт позднего `PAID` после отмены,
admin override, повторный `createPayment`, параллельный промокод с
`usageLimit=1`.

**E2E:** полный сценарий брони и оплаты; `FAILED → retry → PAID`; две
параллельные попытки на один номер/даты → только одна успешна.

### 90.23. Production checklist (для собственного движка)

**Booking:** нет двойных броней; истёкшие hold'ы освобождают номер; цена
считается сервером; промокод/акция проверяются сервером; стык дат
день-в-день разрешён.

**Payment:** ЮKassa работает; webhook идемпотентен; повторный
`createPayment` не дублирует; retry работает; refund создаёт запись и
работает; сумма возвратов не превышает оплаченную; admin override
залогирован.

**Security:** admin auth; authorization; rate limiting; secure cookies;
secrets не в Git; guest token защищён.

**Database:** migrations; indexes; backup; restore procedure проверена.

### 90.24. Альтернативы полному собственному движку (промежуточные варианты)

Если в будущем понадобится больше контроля, чем даёт модуль Bnovo, но
полный собственный движок избыточен — рассмотреть по возрастанию сложности:

1. **iCal-плагин Bnovo** — сайт читает занятость номеров по ссылке iCal
   (экспорт из Bnovo, раздел «Каналы продаж (OTA)»), администратор вручную
   вносит брони с сайта в Bnovo по уведомлению (в мессенджере/email с
   одноразовой подписанной ссылкой подтверждения). Требует собственной
   логики брони/оплаты (см. 90.1–90.23), но не требует платного API.
2. **Bnovo API v2 «Профессионал»** (~34 000 ₽/год на момент оценки,
   сентябрь 2026) — полная двусторонняя синхронизация без ручного шага
   администратора.
3. **Полный отказ от Bnovo** — данные о номерах и бронях полностью
   переезжают в собственную БД (раздел 90.1–90.23), Bnovo как channel
   manager не используется вовсе. Оправдано только при явном решении
   бизнеса отказаться от OTA-каналов или заменить channel manager.

Ручной ввод через RPA-бота/ИИ-агента, кликающего в личном кабинете Bnovo,
**признан нецелесообразным**: не покрывает синхронизацию в обе стороны,
хрупок к изменениям интерфейса Bnovo, рискует нарушить условия
использования Bnovo и по совокупной стоимости (разработка, токены,
починка) не дешевле официальных вариантов уже в первый год.
